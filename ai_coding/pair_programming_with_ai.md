# 如何用 AI 高效编程

这篇文档整理了一些用 AI 写代码的实用技巧。核心思路只有一句：**你负责方向和判断，AI 负责执行和细节**。

这不意味着你可以完全甩手不管——AI 会犯错，会产生幻觉，会给你一个“看起来能跑”但实际上有隐患的实现。你的价值在于知道要做什么、为什么这样做，以及判断 AI 给的东西是否靠谱。

## 用语音输入，把想法快速倒出来

跟 AI 协作，瓶颈往往不在模型，而在你打字的速度。尤其当脑子里有一堆上下文想一次性交代清楚时，一个字一个字敲反而会把思路打断。

语音输入是个被低估的提效手段。比如豆包输入法，边说边转文字，日常表达和口语化描述都够用；如果要给 AI 下任务，也可以选会自动整理结构的那类工具。把“说想法”的成本降下来，你自然更愿意把上下文讲全，AI 的回答质量也会跟着上来。

关于输入工具的更多对比，可以看 [AI 使用实践：Agent 能做什么](/ai_coding/ai_practice_and_boundaries.md)。

## Plan 模式：先规划，再执行

这是我认为最重要的一个习惯。

很多人用 AI 的方式是：直接说“帮我实现 X 功能”，然后 AI 噼里啪啦改了一堆文件，你看着改动不知道从哪里开始审查，最后只能祈祷它没有引入新问题。

更好的方式是**先让 AI 告诉你它打算怎么做，再决定要不要让它做**。

以 Claude Code 为例（其他工具有类似功能，名字可能不同）：

```
你：我想在 VSCode 扩展里加一个“显示当前房间所有成员”的命令，
    先告诉我你打算改哪些文件，不要直接改代码。

AI：我计划修改以下文件：
    1. src/commands.ts - 添加命令处理函数
    2. package.json - 在 contributes.commands 里声明新命令
    3. src/collaboration-room-service.ts - 添加获取成员列表的方法

    不需要修改服务端，因为成员信息已经通过 awareness 同步到客户端了。

你：好，第 3 点不对，成员列表在 collaboration-instance.ts 里，
    你先去看一下那个文件再重新规划。
```

这个来回看起来多了一步，但它让你在 AI 动手之前就能发现方向性错误，省去了事后看一堆改动再回滚的麻烦。

**什么时候用 Plan 模式：**
- 任务涉及超过 2-3 个文件
- 你不确定改动的影响范围
- 这是你第一次接触某个模块

## Goal 模式：设好目标，让它自己跑

Plan 模式解决的是“先想清楚”，Goal 模式解决的是“想清楚之后让它自己跑”。

2026 年，Codex、Claude Code 等工具陆续加入了类似 `/goal` 的命令：你给它一个目标，它进入循环模式，自己调研、写代码、跑测试、修正，直到达成目标（或者卡住、需要你介入）。

它和 Plan 模式的区别在于谁来确认每一步：Plan 模式通常还要你逐段点头，Goal 模式则把“确认”也交给它自己——它自己判断这一步是否达标，然后继续下一步。所以它特别适合长任务：多步骤、耗时、你不想一直盯着点批准。

用法大致是这样：

```text
/goal 修复所有失败的测试，直到 npm test 以状态码 0 退出，且不得修改 /auth 目录之外的文件
```

一个好的 goal 提示最好包含三部分：

- **目标**：一句话说清要做什么。
- **可衡量的完成状态**：怎么算做完，比如 `npm test` 退出码为 0。
- **约束**：哪些东西不能碰。

一些使用经验：

- 一次只设一个 goal，别同时开好几个。
- 短平快的小任务用普通提示就够了，Goal 模式在长任务上才划算。
- 可以配合 Plan 模式用：先用 goal 定方向，再让它规划，做完再清空。
- 学会用暂停和清空（不同工具命令不同，Claude Code 里是 `/pause` 和 `/goal clear`）。
- 它自己跑的时候，最好有能自动验证的东西（测试、lint、构建），否则你没法确认它是不是真的做完了。

> 各家的命令名和开关可能不一样，以你正在用的工具为准。

## 用 @ 符号提供上下文

AI 的回答质量很大程度上取决于你给它的上下文。在支持 @ 引用的工具里（Cursor、Claude Code 等），你可以精确地告诉 AI“我在说哪个文件”。

**@文件**：把具体文件内容带入对话
```
@src/collaboration-instance.ts 这个文件里的 rerenderPresence 方法是做什么的？
```

**@目录**：让 AI 了解整个模块的结构
```
@packages/open-collaboration-yjs 这个包的职责是什么？
```

**@代码块**：选中一段代码后提问（在 IDE 里直接选中再问）
```
（选中 yjs-provider.ts 里的 ocpDataUpdateHandler 方法）
这个方法什么时候会被调用？
```

一个实用原则：**上下文越精准，回答越准确**。不要一次性把整个仓库都 @ 进去，那样 AI 会被淹没在无关信息里。先定位到你关心的模块，再精确引用。

## 提示技巧

### 苏格拉底式提问：先问概念，再问实现

直接让 AI“帮我实现 X”，你得到的是一段代码，但你不一定理解它。更好的方式是先把概念搞清楚，再谈实现。

**不好的方式：**
> "帮我实现一个光标同步功能"

**好的方式：**
> "在这个项目里，光标位置是通过什么机制同步给其他用户的？"

（理解了 awareness 机制之后）

> "awareness 对象里的 cursor 字段是什么格式？在哪里被读取？"

（找到了 collaboration-instance.ts 里的相关代码之后）

> "我想在光标旁边额外显示用户的角色（host/guest），应该改哪里？"

这样一步步问下来，你不只是得到了代码，你还理解了这段代码为什么这样写。下次遇到类似问题，你能自己解决。

### 让 AI 生成多个方案再选择

遇到有多种实现路径的问题时，不要让 AI 直接给你一个实现，先让它列出选项：

> "有哪几种方式可以让 guest 用户在加入房间时自动获取当前所有文件的内容？分别说说优缺点，不要直接写代码。"

AI 可能会给你：
1. 通过 Yjs 的 sync step1/step2 机制（已有实现，改动最小）
2. Host 主动推送文件列表（需要新增消息类型）
3. Guest 主动请求（需要服务端支持）

你选了方案 1 之后，再让 AI 具体实现。这样你对最终代码的理解会深得多，也更容易发现 AI 实现里的问题。

### 用 AI 做代码审查

写完一段代码，或者 AI 帮你生成了一段代码，可以让 AI 帮你找问题：

> "这段代码有什么潜在问题？"

> "如果同时有 50 个用户在同一个房间，这里会有什么性能问题？"

> "这里的错误处理是否完整？如果 WebSocket 断开了会怎样？"

AI 在这种“找茬”模式下往往比“生成”模式更可靠，因为它不需要凭空创造，只需要分析已有的东西。

## 用 Skill 把流程沉淀下来

前面讲的都是“怎么跟 AI 对话”，再往前走一步，是把反复用到的流程固化成 Skill，让 AI 记住该怎么做，而不用你每次重新交代。

Skill 本质上就是一份写给 Agent 的说明书：什么场景用、分几步做、每步用什么工具、有什么注意事项。以 Claude Code、OpenCode 为例，把一份 `SKILL.md` 放进项目的 skills 目录，之后遇到同类任务，Agent 就能按这套流程执行。

哪些东西值得沉淀成 Skill：

- 你反复交代的步骤，比如“新增一个命令并同步更新文档”。
- 有固定检查清单的流程，比如提交前的构建、测试、lint。
- 团队里的约定，比如代码风格、提交规范、目录结构。

一个实用做法：先让 AI 陪你完整做一遍任务，再把过程整理成 `SKILL.md`，下次直接复用。用得越多，Skill 越贴合你的实际工作方式。

## 关于工具选择

这篇文档写于 2026 年 9 月，以 Claude Code 作为示例工具。但 AI 工具的迭代速度极快——可能半年后 Claude Code 已经不是最好的选择，或者它的交互方式已经完全变了。

**重要的不是记住某个工具的具体操作，而是掌握这几条通用原则：**

1. **Plan before execute**：先让 AI 告诉你它打算做什么，再决定要不要让它做。
2. **Set a goal**：长任务设好目标和完成标准，让它自己跑，必要时才介入。
3. **Context is everything**：给 AI 的上下文越精准，结果越好。
4. **Verify before trust**：AI 的输出要验证，不要因为“看起来对”就直接用。
5. **Compound your workflow**：把反复用到的流程沉淀成 Skill，让经验可以复用。

这些原则不会因为工具更新而过时。当你遇到一个新的 AI 工具时，先想想怎么在这个工具里实践这几条原则，而不是去背它的快捷键。

有这样的意识，就算工具变了，你也能很快适应。
