# 与AI结对编程

传统的结对编程是两个人坐在一起，一个写代码，一个看代码。AI结对编程的逻辑类似，只是你的搭档变成了AI：**你负责方向和判断，AI负责执行和细节**。

这不是说你可以完全甩手不管——AI会犯错，会产生幻觉，会给你一个"看起来能跑"但实际上有隐患的实现。你的价值在于知道要做什么、为什么这样做，以及判断AI给的东西是否靠谱。

## Plan模式：先规划，再执行

这是我认为最重要的一个习惯。

很多人用AI的方式是：直接说"帮我实现X功能"，然后AI噼里啪啦改了一堆文件，你看着改动不知道从哪里开始审查，最后只能祈祷它没有引入新问题。

更好的方式是**先让AI告诉你它打算怎么做，再决定要不要让它做**。

以Claude Code为例（其他工具有类似功能，名字可能不同）：

```
你：我想在VSCode扩展里加一个"显示当前房间所有成员"的命令，
    先告诉我你打算改哪些文件，不要直接改代码。

AI：我计划修改以下文件：
    1. src/commands.ts - 添加命令处理函数
    2. package.json - 在 contributes.commands 里声明新命令
    3. src/collaboration-room-service.ts - 添加获取成员列表的方法

    不需要修改服务端，因为成员信息已经通过 awareness 同步到客户端了。

你：好，第3点不对，成员列表在 collaboration-instance.ts 里，
    你先去看一下那个文件再重新规划。
```

这个来回看起来多了一步，但它让你在AI动手之前就能发现方向性错误，省去了事后看一堆改动再回滚的麻烦。

**什么时候用Plan模式：**
- 任务涉及超过2-3个文件
- 你不确定改动的影响范围
- 这是你第一次接触某个模块

## 用@符号提供上下文

AI的回答质量很大程度上取决于你给它的上下文。在支持@引用的工具里（Cursor、Claude Code等），你可以精确地告诉AI"我在说哪个文件"。

**@文件**：把具体文件内容带入对话
```
@src/collaboration-instance.ts 这个文件里的 rerenderPresence 方法是做什么的？
```

**@目录**：让AI了解整个模块的结构
```
@packages/open-collaboration-yjs 这个包的职责是什么？
```

**@代码块**：选中一段代码后提问（在IDE里直接选中再问）
```
（选中 yjs-provider.ts 里的 ocpDataUpdateHandler 方法）
这个方法什么时候会被调用？
```

一个实用原则：**上下文越精准，回答越准确**。不要一次性把整个仓库都@进去，那样AI会被淹没在无关信息里。先定位到你关心的模块，再精确引用。

## 提示技巧

### 苏格拉底式提问：先问概念，再问实现

直接让AI"帮我实现X"，你得到的是一段代码，但你不一定理解它。更好的方式是先把概念搞清楚，再谈实现。

**不好的方式：**
> "帮我实现一个光标同步功能"

**好的方式：**
> "在这个项目里，光标位置是通过什么机制同步给其他用户的？"

（理解了awareness机制之后）

> "awareness对象里的cursor字段是什么格式？在哪里被读取？"

（找到了 collaboration-instance.ts 里的相关代码之后）

> "我想在光标旁边额外显示用户的角色（host/guest），应该改哪里？"

这样一步步问下来，你不只是得到了代码，你还理解了这段代码为什么这样写。下次遇到类似问题，你能自己解决。

### 让AI生成多个方案再选择

遇到有多种实现路径的问题时，不要让AI直接给你一个实现，先让它列出选项：

> "有哪几种方式可以让guest用户在加入房间时自动获取当前所有文件的内容？分别说说优缺点，不要直接写代码。"

AI可能会给你：
1. 通过Yjs的sync step1/step2机制（已有实现，改动最小）
2. Host主动推送文件列表（需要新增消息类型）
3. Guest主动请求（需要服务端支持）

你选了方案1之后，再让AI具体实现。这样你对最终代码的理解会深得多，也更容易发现AI实现里的问题。

### 用AI做代码审查

写完一段代码，或者AI帮你生成了一段代码，可以让AI帮你找问题：

> "这段代码有什么潜在问题？"

> "如果同时有50个用户在同一个房间，这里会有什么性能问题？"

> "这里的错误处理是否完整？如果WebSocket断开了会怎样？"

AI在这种"找茬"模式下往往比"生成"模式更可靠，因为它不需要凭空创造，只需要分析已有的东西。

## 关于工具选择

这篇文档写于2026年初，以Claude Code作为示例工具。但AI工具的迭代速度极快——可能半年后Claude Code已经不是最好的选择，或者它的交互方式已经完全变了。

**重要的不是记住某个工具的具体操作，而是掌握这三条通用原则：**

1. **Plan before execute**：先让AI告诉你它打算做什么，再决定要不要让它做
2. **Context is everything**：给AI的上下文越精准，结果越好
3. **Verify before trust**：AI的输出要验证，不要因为"看起来对"就直接用

这三条原则不会因为工具更新而过时。当你遇到一个新的AI工具时，先想想怎么在这个工具里实践这三条原则，而不是去背它的快捷键。

有这样的意识，就算工具变了，你也能很快适应。
