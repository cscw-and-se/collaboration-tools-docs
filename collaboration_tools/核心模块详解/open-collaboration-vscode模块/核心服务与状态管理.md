# 核心服务与状态管理（Create/Join/Status 都在这条链路上）

如果你要在 VS Code 端做二次开发，我建议你把注意力先放在“服务之间怎么串起来”，而不是一上来就钻同步细节。原因很现实：

- 新人最常遇到的问题，往往是“状态没切换”“工作区没替换”“断开后没清理干净”。这些问题都属于服务层。
- 同步层的问题（Yjs/awareness）当然也会有，但它们通常发生在“你已经成功进入会话”之后。

这一页讲 3 件事：如何恢复连接（tryConnect）、如何把 UI 状态切成“已连接态”（StatusService）、以及一场会话实例如何维护 peer/权限/离开（CollaborationInstance）。

## 1) `tryConnect()`：为什么有时 VS Code 一启动就“自动回到协作会话”

扩展启动时会调用 `roomService.tryConnect()`（见 [项目概览](/collaboration_tools/project_overview.md)）。`tryConnect()` 的意义是：如果上次你是 Guest 并且保存了 roomToken，就尽量把会话恢复回来。

```ts
async tryConnect(): Promise<CollaborationInstance | undefined> {
    const roomData = await this.secretStore.consumeRoomData();
    if (roomData) {
        const connectionProvider = await this.connectionProvider.createConnection(roomData.serverUrl);
        const connection = await connectionProvider.connect(roomData.roomToken, roomData.host);
        const instance = this.instanceFactory({
            connection,
            serverUrl: roomData.serverUrl,
            host: false,
            roomId: roomData.roomId,
            hostId: roomData.host.id
        });
        this.onDidJoinRoomEmitter.fire(instance);
        return instance;
    }
    return undefined;
}
```

这段代码解决的问题是：“把上一次的连接状态延续到下一次启动”。它的上下游很清楚：

- 上游：`activate()` 里调用 tryConnect。
- 下游：恢复成功后会 `fire(instance)`，触发 UI 状态切换（见下一节）。

如果你遇到“Guest 重启后反复尝试连接但马上又断开”，优先看：roomToken 是否过期、server 是否允许该 token 复用、以及 `connection.onDisconnect(() => this.dispose())` 是否被触发（见本文后半段）。

## 2) UI 状态为什么会跟着变：`CollaborationStatusService` 在监听什么

很多人误以为状态栏/TreeView 是“某个地方手动刷新”的。实际上这里是事件驱动的：一旦 `onDidJoinRoom` 触发，就切换状态、挂上 view 数据源、设置 context key，并在 dispose 时反向清理。

```ts
@postConstruct()
protected init(): void {
    this.roomService.onDidJoinRoom(instance => {
        this.setState(instance.host ? StatusBarState.Sharing : StatusBarState.Connected);
        this.viewDataProvider.onConnection(instance);
        this.contextKeyService.setConnection(instance);
        instance.onDidDispose(() => {
            this.setState(StatusBarState.Idle);
            this.contextKeyService.setConnection(undefined);
            if (!instance.host) {
                closeSharedEditors();
                removeWorkspaceFolders();
            }
        });
    });
    this.context.subscriptions.push(
        vscode.window.registerTreeDataProvider('oct.roomView', this.viewDataProvider),
        this.statusBarItem
    );
}
```

这段代码解决的问题是：“当会话状态变化时，UI 必须跟着变化，而且要保证能清理干净”。它的几个关键点：

- Host/Guest 的状态栏文案不同（Sharing vs Collaborating）。
- Guest dispose 时会 `closeSharedEditors/removeWorkspaceFolders`，这解释了“为什么退出会话后 `oct://` 工作区会被移除”。 

如果你二开要增加一个新的 UI 视图（比如显示当前同步状态、显示房间参数），建议也用同样的模式：监听 `onDidJoinRoom` 拿到 `instance`，再订阅 `instance` 的事件。

## 3) 会话实例如何维护 peer/权限/离开：`CollaborationInstance` 的房间事件

`CollaborationInstance` 是“一场会话”的运行时。它不仅负责同步，还要负责“谁加入了、谁离开了、权限变了怎么办”。下面这段代码把这些事件都挂上了：

```ts
connection.peer.onInit(async (_, initData) => {
    await this.initialize(initData);
});
connection.room.onJoin(async (_, peer) => {
    if (this.host) {
        // Only initialize the user if we are the host
        const roots = vscode.workspace.workspaceFolders ?? [];
        const initData: types.InitData = {
            protocol: types.VERSION,
            host: await this.identity.promise,
            guests: Array.from(this.peers.values()).map(e => e.peer),
            capabilities: {},
            permissions: this._permissions,
            workspace: {
                name: vscode.workspace.name ?? 'Collaboration',
                folders: roots.map(e => e.name)
            }
        };
        connection.peer.init(peer.id, initData);
    }
    this.peers.set(peer.id, new DisposablePeer(this.yjsAwareness, peer));
    this.onDidUsersChangeEmitter.fire();
});
connection.room.onPermissions((_, permissions) => {
    this._permissions = permissions;
    this.fileSystemManager?.registerFileSystemProvider(permissions.readonly);
});
```

这段代码在解决三个问题：

- 新用户加入后，Host 负责发 initData（包括 workspace folders、权限等），这样 Guest 才能把工作区切成 `oct://` 并进入同步态。
- `peers` 的维护是实例级别的，它会驱动 presence 渲染、TreeView 用户列表等。
- 权限变更时，会驱动 Guest 侧文件系统 provider 的只读/可写模式切换。

如果你要改“加入后初始化哪些能力”，这里是最关键的改动点：`InitData` 里放了哪些字段，以及 `initialize(initData)` 具体做了什么（通常会影响 workspace、capabilities、permissions 的使用方式）。

## Summary

- `tryConnect()` 决定了“扩展启动时是否恢复会话”，是很多“状态异常”的第一定位点。
- `CollaborationStatusService` 把“会话状态”映射成 UI（状态栏/TreeView/context keys），并负责 dispose 时的清理。
- `CollaborationInstance` 负责“房间事件的运行时”：onJoin 发 initData、维护 peers、响应 permissions。
