# 扩展架构与生命周期（启动、恢复、断线、清理）

VS Code 扩展的“生命周期”决定了很多真实体验：

- 你为什么刚打开 VS Code 就能自动恢复会话（或为什么恢复失败后把工作区清空了）。
- 断线之后，为什么有时还能继续协作（重连 + resync），有时却直接退出会话。
- Guest 退出之后，为什么 `oct://` 工作区会被移除，编辑器也被关掉。

这页按时间线来讲：`activate()` ->（create/join/tryConnect）-> 会话运行 -> 断线/重连 -> `deactivate()`。

## 1) 扩展启动：`activate()` 做了哪些不可逆的事

`activate()` 的代码很短，但它是所有链路的起点：

```ts
export async function activate(context: vscode.ExtensionContext) {
    const container = createContainer(context);
    container.bind(Fetch).toConstantValue(fetch);
    const commands = container.get(Commands);
    commands.initialize();
    const roomService = container.get(CollaborationRoomService);

    const connection = await roomService.tryConnect();
    if (connection) {
        // Wait for the connection to be ready before returning.
        // This allows other extensions that need some workspace information to wait for the data.
        await connection.ready;
    } else {
        await closeSharedEditors();
        removeWorkspaceFolders();
    }
}
```

这段代码解决的问题是：“扩展激活后是否进入协作态”。几个容易忽略的点：

- 先 `commands.initialize()` 再 `tryConnect()`：保证即使恢复失败，你仍然能通过 UI 再次 Join/Create。
- 恢复失败时会清理 `oct://` 工作区：这能避免“残留协作工作区”污染正常工作区，但也会让人误以为“扩展乱删我的 folder”。（它删的是 workspace folders，不会直接删磁盘文件。）

## 2) 会话运行：`CollaborationInstance` 为什么既管同步又管清理

当 create/join/tryConnect 成功，最终都会创建一个 `CollaborationInstance`。这个类在 `init()` 里把会话“点火”，同时也把“退出会话时需要清理的资源”都挂到 `toDispose` 上。

下面这段代码能解释断线/重连的行为：

```ts
this.yjsProvider = new OpenCollaborationYjsProvider(connection, this.yjs, this.yjsAwareness, {
    resyncTimer: 10_000 // resync every 10 seconds
});
this.yjsProvider.connect();
this.toDispose.push(connection);
this.toDispose.push(connection.onDisconnect(() => {
    this.dispose();
}));
this.toDispose.push(connection.onReconnect(() => {
    // Reconnect the Yjs provider
    // This will resync all missed messages
    this.yjsProvider.connect();
}));
this.toDispose.push(this.yjsProvider);
```

这段代码解决的问题是：

- “为什么断线会结束会话”：`onDisconnect` 触发后直接 `dispose()`。
- “为什么重连后能追上”：重连时再跑一次 `yjsProvider.connect()`，会触发同步 step 流程把状态补齐。
- “为什么会周期性 resync”：`resyncTimer` 会每 10 秒主动发 sync step1（在网络抖动时更稳，但也会增加消息量）。

如果你要二开优化稳定性，最常见的两个方向是：

- 调整 `resyncTimer` 策略（比如可配置，或在连接稳定后降低频率）。
- 改 `onDisconnect` 的策略（比如允许短暂断线的“软断开”，而不是立刻 dispose）。这类改动会影响体验和复杂度，需要谨慎。

## 3) Web 模式的特殊点：工作区切换后扩展宿主不一定重启

`joinRoom()` 在 web 模式下做了一个“很工程化但很有效”的补丁：如果工作区 folders 切换后扩展宿主没重启，那就延迟再 tryConnect 一次。

```ts
if (success && isWeb()) {
    // It seems like the web extension mode doesn't restart the extension host upon changing workspace folders
    // However, force restarting the extension host by reloading the window removes the current workspace folders
    // Therefore, we simply attempt to connect after a short delay after receiving the success signal
    setTimeout(() => {
        this.tryConnect();
    }, 500);
}
```

这段代码解决的问题是：“web 端切换 workspace 后，连接状态可能没被正确恢复”。如果你们团队以后要在 vscode.dev 或者 web 版环境里用协作，这段逻辑非常值得保留。

## 4) 扩展停用：`deactivate()` 为什么要做强清理

`deactivate()` 会离开会话并清理残留 UI/工作区：

```ts
export async function deactivate(): Promise<void> {
    await CollaborationInstance.Current?.leave();
    CollaborationInstance.Current?.dispose();
    await closeSharedEditors();
    removeWorkspaceFolders();
}
```

这段代码解决的问题是：“扩展被卸载/重载/窗口关闭时，不留下协作残留状态”。它的副作用是：如果你在调试扩展并频繁 reload extension host，会经常看到工作区 folders 被清空，这是预期行为。

## Summary

- `activate()` 决定扩展启动后的走向：挂命令 -> 尝试恢复 -> 失败则清理协作工作区。
- 会话运行期的断线/重连策略主要在 `CollaborationInstance.init()`：断线 dispose，重连 resync。
- web 模式下 join 后需要额外 `setTimeout(tryConnect)` 来补连接恢复。
- `deactivate()` 做强清理，保证不留残留协作状态。
