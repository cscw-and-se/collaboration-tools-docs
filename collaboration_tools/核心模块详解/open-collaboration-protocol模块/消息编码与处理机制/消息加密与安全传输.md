# 消息加密与安全传输（我们自己的混合加密封装）

这套协作系统里，“加密”不是一个可选装饰，而是协议层默认的工作方式：peer-to-peer 的 request/notification/broadcast 基本都以加密形式在网络上流动，server 主要扮演 relay（中继）角色。

这一页要解决三个你会在排障/二开里反复遇到的问题：

1. 为什么 connect 时必须带 `x-oct-public-key`？
2. 为什么广播消息在接收侧要求 `keys.length === 1`？
3. cache 到底缓存的是什么，为什么要做 cleanup？

## 1. 加密入口：`Encryption.encrypt()` 负责“编码→压缩→对称加密→封装密钥”

加密逻辑在 `packages/open-collaboration-protocol/src/messaging/encryption.ts`。你可以把 `encrypt()` 理解成“把一条 message 的 content 变成不可读的 Uint8Array，并把解密所需的 key 信息写进 metadata”：

```ts
const encoded = Encoding.encode(content);
const compressionAlgo = Compression.bestFit(keys.map(key => key.supportedCompression));
const compressed = await Compression.compress(encoded, compressionAlgo);
const iv = await getCryptoLib().generateIV();
const encrypted = await getCryptoLib().symEncrypt(compressed, key, iv);
const encryptedKeys = await Promise.all(keys.map(async key => {
    let cachedKey = symKey.cache?.[key.peerId];
    if (!cachedKey) {
        cachedKey = toBase64(await getCryptoLib().publicEncrypt(keyBuffer, key.publicKey));
        if (symKey.cache) symKey.cache[key.peerId] = cachedKey;
    }
    return { target: key.peerId, key: cachedKey, iv } as MessageContentKey;
}));
return {
    ...message,
    metadata: { ...message.metadata, encryption: { keys: encryptedKeys }, compression: { algorithm: compressionAlgo } },
    content: encrypted
};
```

这段代码解决的问题是：

- content 用 MessagePack encode 成二进制
- 按目标 peer 支持的压缩算法协商，先压缩（可选）
- 用对称密钥（symmetric key）加密压缩后的 payload
- 用每个接收方的公钥把对称密钥加密一次（形成 `metadata.encryption.keys[]`），这样每个 peer 都能拿到“解自己那份消息所需的 key”

上游怎么到这：`AbstractBroadcastConnection.sendRequest/sendNotification/sendBroadcast` 在 target 不是 `''` 时都会调用 `Encryption.encrypt()`（见 [消息编码与处理机制](/collaboration_tools/核心模块详解/open-collaboration-protocol模块/消息编码与处理机制/消息编码与处理机制.md)）。

下游会发生什么：message.content 变成不可读的 `Uint8Array`，metadata 里写入 keys 与 compression algorithm，接收侧按这些信息解密/解压/解码。

## 2. 解密入口：为什么要求 `keys.length === 1`

`decrypt()` 有一条非常强的断言（同文件）：

```ts
// We always expect exactly one key for every message we receive
// ... even for broadcasts, the server will modify the message to only contain the key for the target peer.
if (message.metadata.encryption.keys.length !== 1) {
    throw new Error('Expected exactly one key for decryption');
}
const key = message.metadata.encryption.keys[0];
const decrypted = await getCryptoLib().symDecrypt(message.content, decryptedKey, key.iv);
const decompressed = await Compression.decompress(decrypted, message.metadata.compression.algorithm);
const decoded = Encoding.decode(decompressed);
return { ...message, content: decoded };
```

这段代码解决的问题是：“接收侧解密必须明确用哪一把 key”。对 request/notification 来说天然只有一个目标，因此 keys 也天然只有一个；**对 broadcast 来说，发送方会生成多把 key（每个 peer 一把）**，但接收侧不应该拿到“别人那把 key”，因此 server 会在 relay 时裁剪，只保留目标 peer 的那一把。

这个“裁剪”逻辑在 server 的 `MessageRelay.sendBroadcast()`（`packages/open-collaboration-server/src/message-relay.ts`）：

```ts
message.origin = origin.id;
for (const peer of room.peers) {
    if (peer !== origin) {
        const peerKey = message.metadata.encryption.keys.find(e => e.target === peer.id);
        if (peerKey && BroadcastMessage.isEncrypted(message)) {
            const messageWithSingleKey: EncryptedBroadcastMessage = {
                ...message,
                metadata: { ...message.metadata, encryption: { keys: [peerKey] } }
            };
            peer.channel.sendMessage(messageWithSingleKey);
        } else if (!Message.isEncrypted(message)) {
            peer.channel.sendMessage(message);
        }
    }
}
```

所以你如果遇到 “Expected exactly one key for decryption”，第一反应不是去改 protocol 的 decrypt，而是去查：

- 这个广播是不是被正确地经过了 server relay（而不是 peer 直接发给 peer）？
- relay 逻辑是否被二开改坏，或者某条 broadcast 走了非预期路径？

## 3. connect 为什么要带公钥：`x-oct-public-key` 是 “别人怎么解你发的消息”

协议层 `connect()` 会生成 key pair，并把公钥放进握手 headers（`packages/open-collaboration-protocol/src/connection-provider.ts`）：

```ts
const metadata = await this.getMetaData();
const transportIndex = this.findFitting(metadata.transports, this.options.transports.map(t => t.id));
const transportProvider = this.options.transports[transportIndex];
const keyPair = await Encryption.generateKeyPair();
const transport = transportProvider.createTransport(this.options.url, {
    'x-oct-jwt': roomAuthToken,
    'x-oct-public-key': keyPair.publicKey,
    'x-oct-client': this.options.client ?? 'Unknown OCT JS Client',
    'x-oct-compression': 'gzip'
});
```

这段代码解决的问题是：“别人要给你发加密消息，就必须拿到你的公钥来包对称密钥”。这也是为什么 server 在接入时会强制要求 `x-oct-public-key`，否则加密链路根本无法成立。

## 4. cache 与 cleanup：缓存的到底是什么，为什么要清空

协议层会缓存两类东西，并且在每次 `handleMessage()` 时做一次清理（`packages/open-collaboration-protocol/src/messaging/abstract-connection.ts`）：

```ts
protected symKey = Encryption.generateSymKey();
protected encryptionKeyCache: Record<string, string> = {};
protected decryptionKeyCache: Record<string, string> = {};
protected maxCacheSize = 50;

protected cleanupCaches(): void {
    // Determine the maximum size of the cache based on the number of available peers/keys
    const maxSize = this.getPublicKeysLength() + this.maxCacheSize;
    if (Object.keys(this.encryptionKeyCache).length > maxSize) {
        this.encryptionKeyCache = {};
    }
    if (Object.keys(this.decryptionKeyCache).length > maxSize) {
        this.decryptionKeyCache = {};
    }
}
```

- `encryptionKeyCache`：缓存 “把对称密钥用某个 peer 公钥加密后的结果”（避免每条消息都重新 publicEncrypt 一次）
- `decryptionKeyCache`：缓存 “某个加密 key 解出来的对称密钥”（避免重复 privateDecrypt）

而 `cleanupCaches()` 的策略很粗暴但很实用：**如果 cache 的 key 数量超过一个上限（peer 数 + 50），就直接清空**，防止 room 频繁进出导致 cache 无限制增长。

这段代码解决的问题是：“协议层宁可牺牲一点重复计算，也不能让 cache 变成内存泄漏点”。

## 5. 算法参数：这里写死了什么

真实算法参数在 `packages/open-collaboration-protocol/src/utils/crypto.ts`。例如 key pair 的生成明确是 RSA-OAEP（4096）+ SHA-256，对称密钥是 AES-CBC（256）：

```ts
const pair = await subtle.generateKey({
    name: 'RSA-OAEP',
    modulusLength: 4096,
    publicExponent: new Uint8Array([1, 0, 1]),
    hash: 'SHA-256'
}, true, ['encrypt', 'decrypt']);
const key = await subtle.generateKey({
    name: 'AES-CBC',
    length: 256
}, true, ['encrypt', 'decrypt']);
```

二开时如果你想替换算法或增加前向安全性（例如引入 ECDH），这里是最硬的“事实入口”，必须先看清楚再动。

## Summary

- `encrypt()` 的真实链路是：encode(content) → bestFit(compression) → compress → symEncrypt → 用各 peer 公钥包对称密钥 → 写入 metadata.encryption.keys。
- `decrypt()` 要求 `keys.length === 1`，因为 broadcast 在 server relay 时会被裁剪成单 key；这是系统设计的一部分，不是“奇怪的限制”。
- connect 时必须带 `x-oct-public-key`，否则别人无法给你发加密消息。
- cache 缓存的是“被公钥加密过的对称密钥”和“已解出的对称密钥”，`cleanupCaches()` 用上限策略防止内存泄漏。
