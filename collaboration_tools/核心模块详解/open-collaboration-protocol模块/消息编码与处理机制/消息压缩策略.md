# 消息压缩策略（压缩协商真实发生在哪里）

压缩这件事很容易被写成“超过多少字节就压缩”这种经验结论，但在 `open-collaboration-protocol` 的当前实现里，**压缩并不是由“消息大小阈值”驱动**，而是由两件事实驱动：

1. 发起连接时，客户端会声明 “我支持哪些压缩算法”（通过 headers 或 peer metadata）
2. 发送加密消息时，会根据“目标 peer 支持的算法集合”选一个 best fit，然后压缩

这一页只讲代码里真正发生的逻辑：压缩声明在哪里、协商在哪里、压缩/解压在哪里。

## 1. 压缩能力从哪里来：握手 headers + peer metadata

协议层 JS client 在 `connect()` 时会把压缩偏好写进 headers（`packages/open-collaboration-protocol/src/connection-provider.ts`）：

```ts
const metadata = await this.getMetaData();
const transportIndex = this.findFitting(metadata.transports, this.options.transports.map(t => t.id));
const transportProvider = this.options.transports[transportIndex];
const keyPair = await Encryption.generateKeyPair();
const transport = transportProvider.createTransport(this.options.url, {
    'x-oct-jwt': roomAuthToken,
    'x-oct-public-key': keyPair.publicKey,
    'x-oct-client': this.options.client ?? 'Unknown OCT JS Client',
    'x-oct-compression': 'gzip'
});
const connection = createConnection({ privateKey: keyPair.privateKey, transport, host });
return connection;
```

这段代码解决的问题是：“让 server 在接入 peer 时就知道这个客户端支持哪些压缩算法”，从而把它存进 peer 的 protocol metadata。

你可以在 server 的 `PeerImpl.toProtocol()` 里看到它如何把 `supportedCompression` 放进 peer metadata（`packages/open-collaboration-server/src/peer.ts`）：

```ts
toProtocol(): protocol.Peer {
    return {
        id: this.id,
        host: this.host,
        name: this.user.name,
        email: this.user.email,
        metadata: {
            compression: { supported: this.peerInfo.supportedCompression },
            encryption: { publicKey: this.publicKey }
        }
    };
}
```

## 2. 协商算法：`Compression.bestFit()` 做的不是“按大小”，而是“求交集”

真正的协商逻辑在 `packages/open-collaboration-protocol/src/messaging/compression.ts`。`bestFit()` 接受一个列表（或列表的列表），核心是：**找所有 peer 都支持的算法，并按各自排序求一个综合最优**：

```ts
export function bestFit(algs: Algorithm[][] | Algorithm[]): Algorithm {
    if (algs.length === 0) {
        return 'none';
    } else if (typeof algs[0] === 'string') {
        return algs[0];
    } else {
        const nested = algs as Algorithm[][];
        const ranking = new Map<Algorithm, number>();
        const first = algs[0];
        for (let i = 0; i < first.length; i++) {
            const alg = first[i];
            if (alg !== 'none') ranking.set(alg, i);
        }
        // ... 在后续列表里累加排名，并剔除不在交集中的算法
        return best;
    }
}
```

这段代码解决的问题是：“广播时可能有多个接收方，必须选一个大家都能解的压缩算法。”它的输入是各 peer 的 `supportedCompression` 集合，而不是消息长度。

## 3. 真正压缩发生在哪里：加密前压缩（compress），解密后解压（decompress）

在 `Encryption.encrypt()` 里，协议层会先 encode content，然后选算法，再压缩，再做对称加密（见 [消息加密与安全传输](/collaboration_tools/核心模块详解/open-collaboration-protocol模块/消息编码与处理机制/消息加密与安全传输.md)）。这意味着：

- 压缩发生在“content 序列化之后”
- 压缩发生在“对称加密之前”
- 因此接收侧必须先对称解密，再按 metadata.algorithm 解压，再 decode

压缩/解压实现本身在 `compression.ts` 里也很直白，但有一个重要的工程取舍：用同步 gzip（`gzipSync/gunzipSync`），因为消息足够小，不值得为异步压缩创建 worker（源码注释就在函数里）：

```ts
export async function compress(data: Uint8Array, alg: Algorithm): Promise<Uint8Array> {
    if (alg === 'none' || alg === undefined) {
        return data;
    } else if (alg === 'gzip') {
        // The sync version is way faster than the async version
        // As each async call spawns a new worker - which is slow
        // Our message size is small enough to not block the main thread
        return fflate.gzipSync(data);
    }
    throw new Error('Unsupported compression algorithm: ' + alg);
}
```

这段代码解决的问题是：“在高频、小包的协作场景里，压缩要便宜，不能为了‘异步’付出更大的调度开销。”

## 常见问题：遇到现象怎么定位

- **“解密成功但 decode 失败/数据结构不对”**：优先看 `message.metadata.compression.algorithm` 是否被写错或被遗漏；压缩算法不一致会直接导致解压/解码失败。
- **“gzip 明明声明了但没生效”**：看目标 peer 的 `supportedCompression` 是否包含 gzip；协商结果由交集决定，不是由你本地单方面决定。

## Summary

- 当前实现里，压缩不是“按消息大小阈值触发”，而是“按 peer 能力协商决定”。
- 能力声明来自 connect headers（`x-oct-compression`）并被 server 写入 peer metadata。
- `Compression.bestFit()` 负责求交集并选最优算法；`compress/decompress` 负责实际数据变换。
- 压缩发生在加密前，解压发生在解密后；两边必须靠 metadata.algorithm 对齐。
