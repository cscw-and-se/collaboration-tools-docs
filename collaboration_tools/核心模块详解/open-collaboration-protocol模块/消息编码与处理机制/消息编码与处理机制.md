# 消息编码与处理机制（消息从哪来，到哪去，为什么能回得来）

这份协议层文档里，我最希望你读完能“脑子里有一条路”：

1. 你调用 `connection.fs.readFile()` 这样的语义 API；
2. 它会被编码、（可选）压缩、（必要）加密，写入 transport；
3. server 把消息作为 peer-to-peer relay 转发给目标；
4. 目标 peer 解密、路由到 handler，执行你的业务逻辑；
5. 如果是 request，会生成 response，再按规则加密回写；
6. 发起方收到 response 后，把 Promise resolve 掉。

这一页主要靠 `AbstractBroadcastConnection`（`packages/open-collaboration-protocol/src/messaging/abstract-connection.ts`）把“消息如何被路由”讲清楚。读这个类时，你可以把它当成一个“消息交换机”。

## 1. 消息长什么样：kind + metadata + content

协议层的消息 envelope 在 `packages/open-collaboration-protocol/src/messaging/messages.ts` 定义。你最常用到的其实是三个 kind：

- `request`：请求，必须有 `id`，对应一个 Promise
- `response / response-error`：对某个 request 的回复（成功/失败）
- `notification / broadcast`：通知/广播，不需要等待返回

所有消息都会带 `metadata`，里面有两件事：

- `encryption.keys`：加密用的 key 列表（广播时会有多把；但**收到时**预期只有一把，原因见 [消息加密与安全传输](/collaboration_tools/核心模块详解/open-collaboration-protocol模块/消息编码与处理机制/消息加密与安全传输.md)）
- `compression.algorithm`：压缩算法（见 [消息压缩策略](/collaboration_tools/核心模块详解/open-collaboration-protocol模块/消息编码与处理机制/消息压缩策略.md)）

## 2. 发起 request：Promise 是怎么被挂起来的

当你调用 `sendRequest` 时，协议层会：

1. 生成 request id
2. 把 `id -> Deferred` 放进 `requestMap`
3. 构造 RequestMessage（origin 固定 `''`）
4. 如果 target 不是 `''`，会加密后写入 transport

源码（`packages/open-collaboration-protocol/src/messaging/abstract-connection.ts`）：

```ts
const id = this.requestId++;
const deferred = new Deferred<any>();
const timeout = setTimeout(dispose, 60_000); // Timeout after one minute
this.requestMap.set(id, { id, response: deferred, dispose });
const message = msg.RequestMessage.create(type, id, '', target, parameters);
if (target === '') {
    await this.write(message);
} else {
    const encryptedMessage = await Encryption.encrypt(message, {
        symmetricKey: this.symKey,
        cache: this.encryptionKeyCache
    }, this.getPublicKey(target));
    await this.write(encryptedMessage);
}
return deferred.promise;
```

这段代码解决的问题是：“让 request 像函数调用一样好用：你 `await` 的其实是一个被 response 驱动的 Deferred。”

- 上游怎么到这：上层调用 `connection.fs.readFile(...)` / `connection.peer.init(...)` 等语义 API。
- 下游会发生什么：消息被写到 transport，等待 server 转发；与此同时 `requestMap` 里挂着一个“等 response 的 Promise”。

## 3. 收到 request：解密、找到 handler、生成 response，再回写

收到 request 的那一侧，会在 `handleMessage()` 里完成“解密→调用→回写”的闭环。下面这段是 request 分支里最核心的部分（同文件）：

```ts
let decrypted: msg.RequestMessage;
if (msg.RequestMessage.isEncrypted(message)) {
    decrypted = await Encryption.decrypt(message, {
        privateKey: this.options.privateKey,
        cache: this.decryptionKeyCache
    });
} else if (msg.RequestMessage.is(message)) {
    decrypted = message;
} else {
    return;
}
const handler = this.messageHandlers.get(decrypted.content.method) ?? this.onUnhandledRequestHandler?.(decrypted.content.method);
await this._ready.promise;
let response: msg.ResponseMessage | msg.ResponseErrorMessage;
try {
    const result = await handler(decrypted.origin, ...(decrypted.content.params ?? []));
    response = msg.ResponseMessage.create(decrypted.id, result);
} catch (error) {
    response = msg.ResponseErrorMessage.create(decrypted.id, String(error));
}
if (decrypted.origin === '') {
    await this.write(response);
} else {
    const publicKey = this.getPublicKey(decrypted.origin);
    const encryptedResponseMessage = await Encryption.encrypt(response, { symmetricKey: this.symKey, cache: this.encryptionKeyCache }, publicKey);
    await this.write(encryptedResponseMessage);
}
```

这段代码解决的问题是：“协议层自己保证 request/response 的对齐，以及 response 的加密策略”。

这里的两个关键点，值得你在排障时反复回来看：

1. **handler 查找是按 `method` 字符串**：`this.messageHandlers.get(decrypted.content.method)`。如果你发了一个 method，但对端没注册 handler，会直接报 “No handler registered…”
2. **`origin === ''` 的特殊含义**：它表示“这是 server 发来的 request”（或者至少被标记成 server-origin）。这种情况下 response 会以明文写回 transport。

## 4. 收到 broadcast/notification：解密后直接分发

broadcast/notification 没有 response，它的处理逻辑也更直白：解密（如果是加密消息）→ 找 handler → 调 handler。源码（同文件）：

```ts
let decrypted: msg.BroadcastMessage | msg.NotificationMessage;
if (msg.NotificationMessage.isEncrypted(message) || msg.BroadcastMessage.isEncrypted(message)) {
    decrypted = await Encryption.decrypt(message, {
        privateKey: this.options.privateKey,
        cache: this.decryptionKeyCache
    });
} else if (msg.NotificationMessage.is(message) || msg.BroadcastMessage.is(message)){
    decrypted = message;
} else {
    return;
}
const handler = this.messageHandlers.get(decrypted.content.method) ?? (msg.BroadcastMessage.is(decrypted) ?
    this.onUnhandledBroadcastHandler?.(decrypted.content.method) :
    this.onUnhandledNotificationHandler?.(decrypted.content.method));
handler(message.origin, ...(decrypted.content.params ?? []));
```

这段代码解决的问题是：“把实时状态（例如 `sync/dataUpdate`、`room/joined`）尽快交给上层，而不是让上层自己处理解密/解码”。

## 5. method 从哪来：`Messages.*` 是整个系统的“方法名字典”

最终路由依赖的是 `method` 字符串。为了避免各处手写字符串、写错一个字符就全线崩溃，`open-collaboration-protocol/src/messages.ts` 集中定义了所有 method（节选）：

```ts
export namespace Messages {
    export namespace Room {
        export const Joined = new BroadcastType<[types.Peer]>('room/joined');
        export const Left = new BroadcastType<[types.Peer]>('room/left');
        export const Leave = new NotificationType<[]>('room/leave');
    }
    export namespace Sync {
        export const DataUpdate = new BroadcastType<[types.Binary]>('sync/dataUpdate');
        export const AwarenessQuery = new BroadcastType<[]>('sync/awarenessQuery');
    }
}
```

你在二开时**如果要加一个新能力**，通常最稳的路径是：

1. 先在这里新增 `Messages.XXX`（决定 method 字符串与类型签名）
2. 再在客户端（vscode/yjs）注册 handler 或发起 sendXXX
3. 最后在 server 里明确它是 “server 处理” 还是 “peer-to-peer relay”

对应的定位捷径在 [协议方法对照表](/collaboration_tools/核心模块详解/open-collaboration-protocol模块/协议方法对照表.md)。

## 常见问题：遇到现象先去哪看

- **“发了 request，但一直等不到 response”**：先看 server 的 relay 是否把 response 回推了（`open-collaboration-server/src/message-relay.ts`），再看 `requestMap` 是否被 timeout dispose（`sendRequest` 的 60s timeout）。
- **“No handler registered for …”**：直接全局搜 method（比如 `sync/awarenessUpdate`）看谁应该注册 handler；通常入口在 VS Code 的 `CollaborationInstance` 或 `FileSystemManager`。
- **“解密报 Expected exactly one key for decryption”**：这是广播 key 没有被 server 裁剪成单 key（见 [消息加密与安全传输](/collaboration_tools/核心模块详解/open-collaboration-protocol模块/消息编码与处理机制/消息加密与安全传输.md)）。

## Summary

- `AbstractBroadcastConnection` 是协议层的“消息交换机”：负责 decode/（解密）/路由/（加密）/回写。
- request 的核心是 `requestMap`：发送时挂 Promise，收到 response 时 resolve/reject。
- `origin === ''` 是一个很关键的分支：它会影响 response 是否加密回写。
- method 字符串统一来自 `open-collaboration-protocol/src/messages.ts`；二开新增能力优先从这里下手。
