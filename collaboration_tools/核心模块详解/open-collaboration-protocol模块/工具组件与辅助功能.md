# 工具组件与辅助功能（你真的会用到的那部分）

`open-collaboration-protocol/src/utils/` 下面有不少工具文件。旧文档常见的问题是：把它们写成“工具百科”，但新人看完并不知道“我现在卡住了，应该用哪个工具定位、哪个工具决定了行为”。

这一页只保留 3 类你在排障与二开里最常真正用到的东西：

1. 事件系统：`Event/Emitter`（为什么所有 transport/connection 都围绕它转）
2. 异步门闩：`Deferred`（ready gate、request/response Promise 的基础）
3. 错误与状态：`Info/ServerError/stringifyError`（为什么有些错误是“服务端可读的 code/message”）

## 1. Event/Emitter：协议层的“统一插座”

协议层大量使用 `Event<T>` 作为事件类型。它的一个关键点是：**Event 本身是一个可调用函数，订阅会返回 Disposable**（源码：`packages/open-collaboration-protocol/src/utils/event.ts`）：

```ts
export interface Event<T> {
    (listener: (e: T) => any, thisArgs?: any, disposables?: Disposable[]): Disposable;
}
export namespace Event {
    const _disposable = { dispose(): void { } };
    export const None: Event<any> = Object.assign(function(): { dispose(): void } { return _disposable; }, {
        get maxListeners(): number { return 0; },
        set maxListeners(maxListeners: number) { }
    });
}
```

这段代码解决的问题是：“订阅与反订阅都有统一语义”，并且支持 `Event.None` 这种“明确没有事件”的表达（你在 WebSocketTransport 的 `onReconnect` 就会看到它）。

你在排障时的一个很好用的读法：

- 看到一个 `Event.None`：说明这条路径**不会发生**某类行为（例如“没有重连事件”）
- 看到一个 `Emitter.fire()`：说明某个行为发生时会向上层冒泡（例如“onDisconnect/onError”）

## 2. Deferred：两个典型用途

`Deferred` 在协议层里出现得非常频繁，因为它比“手搓 Promise resolve/reject”更可控。定义很短（`packages/open-collaboration-protocol/src/utils/promise.ts`）：

```ts
export type MaybePromise<T> = T | Promise<T>;

export class Deferred<T = void> {
    resolve: (value: T) => this;
    reject: (err?: unknown) => this;

    promise = new Promise<T>((resolve, reject) => {
        this.resolve = (arg) => (resolve(arg), this);
        this.reject = (err) => (reject(err), this);
    });
}
```

在协作协议里，它最常见的两个用途是：

1. **ready gate**：transport 连接没 ready 前，write 不应该发（Socket.IO/WebSocket transport 里都这么做）
2. **request/response**：发 request 时挂一个 `Deferred` 进 map，收到 response 后 resolve/reject（`AbstractBroadcastConnection.sendRequest()`）

这也是为什么你看到“卡住”的现象时，经常要去追 `ready.promise` 或 `deferred.promise`：它们才是真正的等待点。

## 3. Info/ServerError：把“可本地化的状态码”从 server 带回 client

协议层的 HTTP API（login/create/join/poll）会从 server 返回一些结构化的状态信息（例如 `JoinTimeout/JoinRejected`）。这些信息在协议层用 `Info` 表示（`packages/open-collaboration-protocol/src/utils/info.ts`）：

```ts
export interface Info {
    code: string;
    params: string[];
    message: string;
}
export namespace Info {
    export function is(arg: unknown): arg is Info {
        return isObject<Info>(arg)
            && typeof arg.code === 'string'
            && typeof arg.message === 'string'
            && Array.isArray(arg.params)
            && arg.params.every(param => typeof param === 'string');
    }
}
```

当 client 把这个错误当成异常抛出来时，会被包装成 `ServerError`（`packages/open-collaboration-protocol/src/utils/errors.ts`）：

```ts
export class ServerError extends Error {

    code: string;
    params: string[];

    constructor(info: Info) {
        super(info.message);
        this.code = info.code;
        this.params = info.params;
    }

}

export function stringifyError(error: unknown, localization?: (info: Info) => string): string {
    if (error instanceof ServerError || Info.is(error)) {
        if (localization) {
            return localization(error);
        }
        return error.message;
    }
    if (error instanceof Error) {
        return error.message;
    }
    return String(error);
}
```

这段代码解决的问题是：“错误不再只有一段 message，而是带 code/params，可以被上层做本地化或更精确的提示”。

因此你在排障 join/login 的问题时，不要只看 `error.message`，要看：

- `error instanceof ServerError` 时的 `error.code`
- `JoinTimeout/JoinRejected/RoomNotFound` 这些 code 从哪条 server 路径发出来

## Summary

- `Event/Emitter` 是协议层的统一事件系统，transport/connection 的生命周期都靠它暴露出来。
- `Deferred` 是两类等待点的基础：ready gate 与 request/response。
- `Info/ServerError` 让协议层能把“结构化状态码”从 server 带回 client，排障时请优先看 `code` 而不是只看 message。
