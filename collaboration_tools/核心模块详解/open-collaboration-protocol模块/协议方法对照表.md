# 协议方法对照表（method 从哪来，谁发起，谁处理，代码入口在哪）

新人排障和二开最痛的点，经常不是“不会写代码”，而是**不知道消息在系统里怎么跑**：你看到一个 method（例如 `fileSystem/readFile`），但你不知道：

- 它是 request/notification/broadcast 哪一种？
- 谁发起（Host/Guest/Server）？
- 谁处理？是在 server 端处理，还是 server 只是 relay，真正处理在另一个 peer？
- VS Code 端的 handler / 调用点在哪个文件里？

这页就是为了解决这个问题：把 method 从 `open-collaboration-protocol/src/messages.ts` 出发，一次性对齐到 server/vscode 的真实入口。

> 约定：下面 “Protocol 入口” 指 `collaboration-tools/packages/open-collaboration-protocol/src/messages.ts` 的 `Messages.*` 常量定义；  
> “Server 入口” 指 `open-collaboration-server` 中创建/转发/处理该消息的关键位置；  
> “VS Code 入口” 指 `open-collaboration-vscode` 中注册 handler 或发起 send 的关键位置。

## 核心方法（常用 20+）

| method | kind | 发起方 | 处理方 | Protocol 入口 | Server 入口 | VS Code 入口 | 备注 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `peer/join` | request | Server（转发 Guest 的加入请求） | Host | `Messages.Peer.Join` | `open-collaboration-server/src/room-manager.ts:requestJoin()` 创建 `RequestMessage.create(Messages.Peer.Join, ..., room.host.id, [user])` 并 `messageRelay.sendRequest(...)` | `open-collaboration-vscode/src/collaboration-instance.ts:connection.peer.onJoinRequest(...)` | Host 的 Allow/Deny 直接决定 Guest 能否拿到 roomToken |
| `peer/info` | notification | Server | Host/Guest（各自接收自己的 peer info） | `Messages.Peer.Info` | `open-collaboration-server/src/room-manager.ts`（join 时发送 Info） | `open-collaboration-vscode/src/collaboration-instance.ts:connection.peer.onInfo(...)` | VS Code 侧用它把 `peer.id` 写进 awareness，并 resolve identity |
| `peer/init` | notification | Host | Guest | `Messages.Peer.Init` | `open-collaboration-server/src/peer.ts` 作为 relay 转发 notification | `open-collaboration-vscode/src/collaboration-instance.ts:connection.peer.onInit(...)`（Guest 接收并 initialize） + `connection.peer.init(peer.id, initData)`（Host 发送） | Host 会把 workspace/folders、permissions、guest 列表等一次性发给新加入者 |

## 你应该如何用这张表排障（3 个最常见场景）

1. **Join 卡住**：先查 `peer/join`。server 端是否真的发出了 request（`room-manager.ts:requestJoin`），Host 端是否真的弹窗并返回 workspace。
2. **Guest 看不到文件/读文件报错**：查 `fileSystem/readFile/stat/readDir`。Host 端 handler 是否注册、是否返回了正确的 `vscode.workspace.fs.*` 结果；server 是否拦截了“未加密 request”（`peer.ts` 会直接 warn 并 return）。
3. **光标/选区不同步**：查 `sync/awarenessQuery` 与 `sync/awarenessUpdate`。Yjs provider 是否在 connect 时发 query、是否在收到 update 时 applyAwarenessUpdate。

## Summary

- method 的唯一“字典”入口是 `open-collaboration-protocol/src/messages.ts`，从这里出发能最稳地追到 server/vscode/yjs。
- 很多协作逻辑不是 server 处理，而是 server 作为 relay：真正的 handler 在另一端 peer（尤其是 fileSystem 与 join approval）。
- 排障优先按“现象 → method → kind → 发起方/处理方 → 代码入口”走，效率会高很多。
