# 用户与对等节点管理（User vs Peer，以及重连为什么能复用）

在 server 端，“用户”和“连接”不是同一个东西：

- `User` 更像身份信息（name/email/provider/id）。
- `Peer` 更像一个活着的会话端点（带 jwt、公钥、client 类型、底层 transport 通道），它会加入某个 room，并参与消息收发。

理解 User/Peer 的区别，能帮你快速搞清楚：为什么同一个人断线重连后还能继续协作、为什么 join 时 Host 能看到对方的 email/provider、以及“踢人”到底踢的是谁（通常踢的是 peer）。

## 1) PeerManager：为什么以 `jwt` 为 key 管理 peer

`PeerManager` 的实现非常短，但它决定了“重连复用”的策略：以 `peer.jwt` 作为 key 存储 peer。

```ts
register(peer: Peer): void {
    this.peers.set(peer.jwt, peer);
    peer.onDispose(() => this.peers.delete(peer.jwt));
}

getPeer(jwt: string): Peer | undefined {
    return this.peers.get(jwt);
}
```

这段代码解决的问题是：“同一个 JWT 的连接，应该对应同一个 peer”。它的直接后果是：

- 客户端如果用同一个 roomToken（JWT）重连，server 会认为这是同一个会话端点的恢复（复用 peer）。
- 一旦 peer dispose，会自动从 map 里清理掉，避免内存泄漏。

这和 `connectChannel()` 里的 `existingPeer` 分支是配套的（见 [open-collaboration-server 模块](/collaboration_tools/核心模块详解/open-collaboration-server模块/open-collaboration-server模块.md)）。

## 2) PeerImpl：一条连接如何变成可路由的消息端点

`PeerImpl.initialize()` 把底层 transport 包装成 `Channel`，并把所有 incoming 消息统一交给 `receiveMessage()` 分流：

```ts
protected initialize(): void {
    this._channel = new Channel(this.peerInfo.channel);
    this._channel.onMessage(message => this.receiveMessage(message));
    this._channel.onClose(() => this.dispose());
}
```

这段代码解决的问题是：“peer 的生命周期要绑定到底层连接”。所以当 socket 断开，`onClose` 会触发 dispose，进而触发 PeerManager/RoomManager 的清理逻辑。

## 3) receiveMessage：为什么未加密的 request/broadcast 会被丢弃

`receiveMessage()` 是 server 侧消息安全与路由的核心位置之一：它会先做版本兼容校验，然后对 request/notification/broadcast 做加密要求。

下面这段代码展示了 request/broadcast 的关键分支：

```ts
} else if (protocol.RequestMessage.isAny(message)) {
    if (!protocol.Message.isEncrypted(message)) {
        this.logger.warn(`Received unencrypted request from: '${this.id}'`);
        return;
    }
    message.origin = this.id;
    try {
        const response = await this.messageRelay.sendRequest(this.getTargetPeer(message.target), message);
        response.id = message.id;
        this.channel.sendMessage(response);
    } catch (_error) {
        const errorResponseMessage = protocol.ResponseErrorMessage.create(message.id, 'Failed to retrieve the requested data.');
        this.channel.sendMessage(errorResponseMessage);
    }
} else if (protocol.BroadcastMessage.isAny(message)) {
    if (!protocol.Message.isEncrypted(message)) {
        this.logger.warn(`Received unencrypted broadcast from: '${this.id}'`);
        return;
    }
    this.messageRelay.sendBroadcast(this, message);
}
```

这段代码解决的问题是：“把安全要求写死在入口处”。所以如果你在客户端看到“某些请求无响应”，不要只盯 UI：也要考虑 server 端是否因为未加密而直接丢弃了消息。

## Summary

- `User` 是身份；`Peer` 是一条活着的连接端点，负责加入房间并参与消息收发。
- `PeerManager` 以 JWT 为 key 管理 peer，这是“重连复用”的核心策略。
- `PeerImpl` 把底层 transport 封装成 Channel，并在入口处强制加密要求。
