# 服务架构与启动流程（从 `listen` 到可用的协作 server）

如果你只是“能跑起来”，你可能只关心命令行输出那句 listening。但如果你要二次开发，你需要知道 server 启动过程中到底做了哪些事：

- HTTP API 什么时候挂上（登录、创建房间、join/poll）？
- Socket.IO 什么时候开始接受连接？连接失败会不会自动断开？
- 认证端点（simple login / OAuth / Keycloak）什么时候注册？认证完成后 JWT 是谁生成的？

这一页按启动顺序讲，并穿插关键源码片段让你能快速定位。

## 1) Socket.IO 接入：连接失败为什么会被立刻断开

server 使用 Socket.IO 接入实时连接。关键点是：每一条 socket 连接都会尝试走 `connectChannel()`，失败就直接 `disconnect(true)`。

```ts
io.on('connection', async socket => {
    const headers = socket.request.headers as Record<string, string>;
    try {
        await this.connectChannel(headers, new SocketIoChannel(socket));
    } catch (error) {
        socket.disconnect(true);
        this.logger.error('Socket IO connection failed', error);
    }
});
```

这段代码解决的问题是：“不让不合法的连接进入房间状态机”。它的下游就是 `connectChannel()`（见 [open-collaboration-server 模块](/collaboration_tools/核心模块详解/open-collaboration-server模块/open-collaboration-server模块.md)），你遇到连不上时最常见的错误也是从那里抛出来的：缺 JWT、缺公钥、JWT 不合法等。

## 2) API 路由：`/api/login/initial` 为什么要先 `startAuth()`

客户端登录流程不是“POST 用户名密码 -> 立刻返回 token”，而是两段式：

1. `/api/login/initial`：server 先生成一个 `pollToken`（confirmToken），同时返回“有哪些登录 provider、登录页 URL 是什么”。
2. 客户端走各自 provider 的流程（比如 simple login 表单、OAuth 跳转）。
3. 客户端再轮询 `/api/login/poll/:token` 等待 JWT 就绪。

下面这段代码就是第一段：生成 pollToken，并返回登录页和 provider 列表。

```ts
app.post('/api/login/initial', async (req, res) => {
    try {
        const token = await this.credentials.startAuth();
        let loginPage: string;
        try {
            const loginPageURL = new URL(loginPageUrlConfig);
            loginPageURL.searchParams.set('token', token);
            loginPage = loginPageURL.toString();
        } catch (_error) {
            loginPage = `/login.html?token=${encodeURIComponent(token)}`;
        }
        // Ensure that we don't send inactive auth providers to the client
        const activeAuthProviders = this.authEndpoints.filter(e => e.shouldActivate());
        const result: LoginInitialResponse = {
            pollToken: token,
            auth: {
                loginPageUrl: loginPage,
                providers: activeAuthProviders.map(endpoint => endpoint.getProtocolProvider()),
                defaultSuccessUrl: this.configuration.getValue('oct-login-success-url') ?? ''
            }
        };
        res.status(200);
        res.send(result);
    } catch (error) {
        this.logger.error('Error occurred during login', error);
        res.status(400);
        res.send('Failed to login');
    }
});
```

这段代码解决的问题是：“让客户端知道该怎么登录，并给后续认证流程一个可轮询的 token”。你做二开时常见改动点：

- 你们想把登录页接到自研页面（`oct-login-page-url` 配置）。
- 你们想改 provider 的展示顺序/默认 provider。

## 3) 认证端点的挂载：认证成功事件最终落到 `confirmUser()`

server 启动后会遍历所有 `authEndpoints`，只激活 `shouldActivate()` 返回 true 的端点。端点完成认证后，会通过 `onDidAuthenticate` 抛出事件，最终由 `CredentialsManager.confirmUser()` 生成 JWT。

```ts
for (const authEndpoint of this.authEndpoints) {
    if (authEndpoint.shouldActivate()) {
        authEndpoint.onStart(app, String(opts.hostname), Number(opts.port));
        authEndpoint.onDidAuthenticate(async event => {
            try {
                await this.credentials.confirmUser(event.token, event.userInfo);
            } catch (err) {
                this.logger.error('Failed to confirm user', err);
                throw new Error('Failed to confirm user');
            }
        });
    }
}
```

这段代码解决的问题是：“把不同认证方式统一收敛到同一个 JWT 生成入口”。因此你要新增/替换认证方式，最安全的做法是：

- 新写一个 `AuthEndpoint`，负责自己的 UI/回调/校验。
- 认证完成后只需要 fire `AuthSuccessEvent`，把 `userInfo` 交给 `confirmUser()` 走统一逻辑。

认证细节建议你读 [认证与安全接入](/collaboration_tools/核心模块详解/open-collaboration-server模块/认证与安全接入/认证与安全接入.md)（如果你们主要用 simple login，就从 [简易登录机制](/collaboration_tools/核心模块详解/open-collaboration-server模块/认证与安全接入/简易登录机制.md) 开始）。

## Summary

- Socket.IO 接入层做了强校验：`connectChannel()` 失败就断开连接。
- 登录是两段式：`/api/login/initial` 先发 pollToken + providers，客户端按 provider 完成认证后再轮询拿 JWT。
- 多种认证方式最终统一落到 `CredentialsManager.confirmUser()`：这是你二开认证时最值得保留的“统一收口”。
