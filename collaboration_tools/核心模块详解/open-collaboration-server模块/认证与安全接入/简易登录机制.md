# 简易登录机制（Simple Login：表单登录是怎么接到 JWT 的）

你们在开发/内网环境里最常用的认证方式通常就是 simple login：用户填一个 name（可选 email），server 就给一个 JWT。

这套机制的“安全等级”显然不如 OAuth/Keycloak，但它的工程价值很大：能让你把注意力放在协作主链路（create/join/sync/fs 代理）上，而不是先被复杂登录流程卡住。

这一页把 simple login 从“server 暴露 provider -> 前端提交表单 -> 触发认证事件 -> 签 JWT -> 客户端 poll 拿 token”这条链路讲清楚。

## 1) server 如何告诉客户端“我支持 simple login”：`getProtocolProvider()`

simple login 端点实现了 `AuthEndpoint.getProtocolProvider()`，返回一个 `FormAuthProvider`。这段返回值非常重要：它决定了客户端会展示哪些字段、字段的 label/placeholder 是什么。

```ts
getProtocolProvider(): FormAuthProvider {
    return {
        type: 'form',
        name: 'unverified',
        endpoint: SimpleLoginEndpoint.ENDPOINT,
        label: { code: Info.Codes.UnverifiedLoginLabel, message: 'Unverified', params: [] },
        details: { code: Info.Codes.UnverifiedLoginDetails, message: 'Login with a user name and an optional email address', params: [] },
        group: { code: Info.Codes.BuiltinsGroup, message: 'Builtins', params: [] },
        fields: [
            { name: 'user', required: true, placeHolder: { code: Info.Codes.UsernamePlaceholder, message: 'Your user name that will be shown to all session participants', params: [] }, label: { code: Info.Codes.UsernameLabel, message: 'Username', params: [] } },
            { name: 'email', required: false, placeHolder: { code: Info.Codes.EmailPlaceholder, message: 'Your email that will be shown to the host when joining the session', params: [] }, label: { code: Info.Codes.EmailLabel, message: 'Email', params: [] } }
        ]
    };
}
```

这段代码解决的问题是：“客户端不用写死表单结构”。如果你们要在内部环境里扩展更多字段（比如部门/学号），最自然的改动点就在这里：新增 `fields` 并在 `onStart()` 校验后写进 `userInfo`。

## 2) 表单提交后 server 做了什么：`onStart()` 的 POST handler

`onStart(app)` 会注册 `POST /api/login/simple`。它做的事情很朴素：校验必填字段，然后 fire 一个认证成功事件。

```ts
app.post(SimpleLoginEndpoint.ENDPOINT, async (req, res) => {
    try {
        const token = req.body.token as string;
        const user = req.body.user as string;
        const email = req.body.email as string | undefined;

        if (!token) {
            res.status(400);
            res.send('No token provided');
            return;
        }
        if (!user) {
            res.status(400);
            res.send('No user provided');
            return;
        }

        await Promise.all(this.authSuccessEmitter.fire({ token, userInfo: { name: user, email, authProvider: 'Unverified' } }));
        res.send('Ok');
    } catch (err) {
        res.status(400);
        res.send('Failed to perform simple login');
    }
});
```

这段代码解决的问题是：“把表单输入变成统一的 `AuthSuccessEvent`”。注意 `token` 是客户端之前从 `/api/login/initial` 拿到的 pollToken（confirmToken），它把“这个表单提交”与“某个正在等待登录结果的轮询”关联起来。

## 3) 事件被谁消费：`confirmUser()` 才是 JWT 的签发点

simple login endpoint 自己不签 JWT，它只 fire 事件。真正签 JWT 的地方在 `CredentialsManager.confirmUser()`，并且是由 `CollaborationServer` 在启动时统一注册的事件回调来调用（见 [认证与安全接入](/collaboration_tools/核心模块详解/open-collaboration-server模块/认证与安全接入/认证与安全接入.md)）。

`confirmUser()` 的核心逻辑是“注册用户 -> 生成 JWT -> 更新 delayedAuth”：

```ts
const registeredUser = await this.userManager.registerUser(user);
const userClaim: User = {
    id: registeredUser.id,
    name: registeredUser.name,
    email: registeredUser.email,
    authProvider: registeredUser.authProvider
};
const jwt = await this.generateJwt(userClaim);
auth.update(jwt);
return jwt;
```

这段代码解决的问题是：“让 provider 只负责拿到 userInfo，让 CredentialsManager 统一签发 JWT”。这也是我建议你们二开时尽量保留的边界：扩展 provider，不要把 JWT 逻辑散落到各处。

## Summary

- simple login 的三段链路：`getProtocolProvider()` 声明表单字段 -> `POST /api/login/simple` 校验并 fire 事件 -> `confirmUser()` 统一签 JWT。
- `token`（pollToken/confirmToken）把表单提交与登录轮询关联起来，是这套机制的关键。
- 如果你们要扩展字段，优先改 `fields` 与 `userInfo`，不要改 poll/JWT 主链路。
