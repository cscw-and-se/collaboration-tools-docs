# 认证与安全接入（默认用什么、token 怎么走、哪里改最安全）

这个项目的认证看起来“支持很多种”（simple login / OAuth / Keycloak），但对新人来说最重要的是把一条主线先跑清楚：

1. 客户端先拿到一个 `pollToken`（confirm token）。
2. 客户端通过某个 provider 完成认证（比如 simple login 表单提交 user/email）。
3. server 端把 `pollToken + userInfo` 变成 JWT（loginToken）。
4. 客户端再用 JWT 去创建房间 / join 房间，并最终用 roomToken 建实时连接。

这一页把这条主线串起来，并告诉你们二次开发时，最安全的改动点在哪。

## 1) 认证入口：`/api/login/initial` 为什么要返回 providers

客户端登录不是“直接弹一个输入框”，而是先问 server：“你支持哪些登录方式、登录页在哪”。

server 的 `/api/login/initial` 会生成一个 `pollToken`，并把当前激活的 providers 列出来：

```ts
const token = await this.credentials.startAuth();
// Ensure that we don't send inactive auth providers to the client
const activeAuthProviders = this.authEndpoints.filter(e => e.shouldActivate());
const result: LoginInitialResponse = {
    pollToken: token,
    auth: {
        loginPageUrl: loginPage,
        providers: activeAuthProviders.map(endpoint => endpoint.getProtocolProvider()),
        defaultSuccessUrl: this.configuration.getValue('oct-login-success-url') ?? ''
    }
};
res.status(200);
res.send(result);
```

这段代码解决的问题是：“客户端无需硬编码认证方式”。二开时最安全的改法也是围绕 `AuthEndpoint.getProtocolProvider()`：你可以新增 provider，但不要直接改协议层或 room 流程。

## 2) provider 如何把认证结果交给 server：事件最终落到 `confirmUser()`

server 在启动时会激活 `authEndpoints`，并把它们的“认证成功事件”统一收敛到 `CredentialsManager.confirmUser()`：

```ts
for (const authEndpoint of this.authEndpoints) {
    if (authEndpoint.shouldActivate()) {
        authEndpoint.onStart(app, String(opts.hostname), Number(opts.port));
        authEndpoint.onDidAuthenticate(async event => {
            await this.credentials.confirmUser(event.token, event.userInfo);
        });
    }
}
```

这段代码解决的问题是：“无论你用 simple login 还是 OAuth，最后都只需要产出 `userInfo`”。因此你如果要替换认证方式，最安全的做法是：

- 保持 `confirmUser(confirmToken, userInfo)` 作为统一收口。
- 新增/替换 `AuthEndpoint`，不要去改 `RoomManager` 的 join 主链路。

## 3) `CredentialsManager`：`startAuth()` 与 `confirmUser()` 在做什么

`CredentialsManager` 维护一个 `deferredAuths`：key 是 confirmToken（pollToken），value 是“未来某一刻会出现 JWT 的承诺”。

`startAuth()` 生成 confirmToken，并设置 5 分钟超时：

```ts
async startAuth(): Promise<string> {
    const confirmToken = this.secureId();
    const updateEmitter = new Emitter<string>();
    const failureEmitter = new Emitter<Error>();
    const dispose = () => {
        clearTimeout(timeout);
        this.deferredAuths.delete(confirmToken);
        updateEmitter.dispose();
        failureEmitter.dispose();
    };
    const timeout = setTimeout(() => {
        failureEmitter.fire(new Error('Request timed out'));
        dispose();
    }, 300_000); // 5 minutes of timeout
    const delayedAuth: DelayedAuth = { update: jwt => { delayedAuth.jwt = jwt; updateEmitter.fire(jwt); }, onUpdate: updateEmitter.event, onFail: failureEmitter.event, dispose };
    this.deferredAuths.set(confirmToken, delayedAuth);
    return confirmToken;
}
```

而 `confirmUser()` 会把 `userInfo` 注册成 `User`，再签出 JWT，并通过 delayedAuth 更新给轮询端：

```ts
async confirmUser(confirmToken: string, user: UserInfo): Promise<string> {
    const auth = this.deferredAuths.get(confirmToken);
    if (!auth) {
        throw this.logger.createErrorAndLog('Login timed out');
    }
    const registeredUser = await this.userManager.registerUser(user);
    const userClaim: User = { id: registeredUser.id, name: registeredUser.name, email: registeredUser.email, authProvider: registeredUser.authProvider };
    const jwt = await this.generateJwt(userClaim);
    auth.update(jwt);
    return jwt;
}
```

这两段代码解决的问题是：“认证过程可能跨页面/跨时间，但客户端仍然能用 pollToken 轮询拿到最终 JWT”。

## 4) 客户端侧：`ConnectionProvider.login()` 为什么一定会 poll

客户端侧（protocol 包）的 `ConnectionProvider.login()` 也把这个“两段式流程”写得很清楚：先 `POST /api/login/initial`，拿到 `confirmToken`，再启动 `pollLogin(confirmToken)`。

```ts
const loginResponse = await this.fetch(this.getUrl('/api/login/initial'), { method: 'POST' });
const loginBody = await loginResponse.json();
const confirmToken = loginBody.pollToken;
// ... authenticationHandler(confirmToken, loginBody.auth)
const authToken = await this.pollLogin(confirmToken, { ...options, abortSignal });
this.userAuthToken = authToken;
return authToken;
```

如果你们之后要做“无 UI 的自动登录”或“接入公司统一登录”，建议优先改 `authenticationHandler` 的实现，而不是去改 poll 机制本身。

## Summary

- 认证主线是“两段式 + 轮询”：`/api/login/initial` 生成 pollToken，provider 完成认证后 `confirmUser()` 产 JWT，客户端再 poll 拿到。
- server 端最安全的扩展点是 `AuthEndpoint`：新增 provider，但把最终收口交给 `CredentialsManager.confirmUser()`。
- 客户端侧最安全的扩展点是 `authenticationHandler`：决定怎么打开登录页/收集表单/完成 OAuth。
