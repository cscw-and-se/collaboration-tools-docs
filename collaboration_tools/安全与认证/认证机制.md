# 认证机制（从登录到 roomToken：新人最常卡的那条链路）

你在协作系统里看到的“认证”，通常不止一次：

- 第一次认证发生在“登录”，拿到用户级 JWT（loginToken）。
- 第二次认证发生在“加入房间”，拿到房间级 JWT（roomToken）。
- 第三次（隐含）认证发生在“实时连接接入”，server 用 `x-oct-jwt` 校验你是否属于某个 room。

这一页不讲 OAuth 教科书，只把“从登录到 roomToken”这条新人最常卡住的链路讲透，并把关键代码片段贴出来。

## 1) 登录为什么要先拿 pollToken：`startAuth()` 的设计意图

server 的登录入口会先生成一个 confirmToken（pollToken），并设置 5 分钟超时。你可以把它理解成：“给这次登录流程分配一个临时的会话编号”。

```ts
async startAuth(): Promise<string> {
    const confirmToken = this.secureId();
    const timeout = setTimeout(() => {
        failureEmitter.fire(new Error('Request timed out'));
        dispose();
    }, 300_000); // 5 minutes of timeout
    const delayedAuth: DelayedAuth = {
        update: jwt => { delayedAuth.jwt = jwt; updateEmitter.fire(jwt); },
        onUpdate: updateEmitter.event,
        onFail: failureEmitter.event,
        dispose
    };
    this.deferredAuths.set(confirmToken, delayedAuth);
    return confirmToken;
}
```

这段代码解决的问题是：“认证过程可能跨页面/跨时间，但客户端仍然能靠一个 token 来 poll 结果”。

## 2) simple login 如何把表单输入变成 `userInfo`

在你们常用的 simple login 场景里，客户端会带着 pollToken 把表单提交到 `/api/login/simple`。server 校验后 fire 认证成功事件：

```ts
const token = req.body.token as string;
const user = req.body.user as string;
const email = req.body.email as string | undefined;

if (!token) { res.status(400); res.send('No token provided'); return; }
if (!user)  { res.status(400); res.send('No user provided'); return; }

await Promise.all(this.authSuccessEmitter.fire({ token, userInfo: { name: user, email, authProvider: 'Unverified' } }));
res.send('Ok');
```

这段代码解决的问题是：“provider 负责拿到 userInfo，但不负责签 JWT”。签 JWT 的统一入口在下一节。

## 3) JWT 由谁签：`confirmUser()` 才是唯一收口

`confirmUser(confirmToken, userInfo)` 会注册用户，并签发 JWT，然后把 JWT 写回 deferredAuth，让客户端轮询接口能取到。

```ts
const registeredUser = await this.userManager.registerUser(user);
const userClaim: User = {
    id: registeredUser.id,
    name: registeredUser.name,
    email: registeredUser.email,
    authProvider: registeredUser.authProvider
};
const jwt = await this.generateJwt(userClaim);
auth.update(jwt);
return jwt;
```

这段代码解决的问题是：“无论你用哪种登录方式，最终都走同一个 JWT 签发逻辑”。这对二开非常重要：你扩展 provider 时，不要把 JWT 逻辑拆散。

## 4) client 侧为什么一定会 poll：`ConnectionProvider.login()` 的行为

客户端侧的 `ConnectionProvider.login()` 会：

1. POST `/api/login/initial` 拿到 pollToken + provider 列表。
2. 调用 `authenticationHandler(...)` 去完成 UI 登录。
3. `pollLogin(confirmToken)` 等到 server 产出 loginToken。

```ts
const loginResponse = await this.fetch(this.getUrl('/api/login/initial'), { method: 'POST' });
const loginBody = await loginResponse.json();
const confirmToken = loginBody.pollToken;
this.options.authenticationHandler(confirmToken, { ...loginBody.auth, loginPageUrl: fullUrl }).then(/* ... */);
const authToken = await this.pollLogin(confirmToken, { ...options, abortSignal });
this.userAuthToken = authToken;
return authToken;
```

这段代码解决的问题是：“把各种认证方式统一成一个 Promise<LoginToken>”。

## Summary

- 认证分两段：先登录拿 loginToken，再 join 房间拿 roomToken（JWT）。
- pollToken 是登录的临时会话编号，5 分钟超时。
- provider 只负责产出 `userInfo`；JWT 签发必须统一收敛到 `confirmUser()`。
- client 侧 `ConnectionProvider.login()` 的核心行为是 poll；要做自动化登录，应优先改 `authenticationHandler`。
