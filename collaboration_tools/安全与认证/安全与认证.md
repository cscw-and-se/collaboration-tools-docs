# 安全与认证（我们默认怎么用，以及你应该在哪些地方小心改）

这套协作系统既有“传统意义的认证”（谁是用户、谁能创建/加入房间），也有“协作场景下的通信安全”（消息是否加密、广播密钥如何分发、未加密消息是否直接丢弃）。

文档层面我们不把它写成百科，而是站在团队真实使用的角度回答三个问题：

1. 我们默认用哪种登录？
2. token 在系统里怎么走？
3. 二次开发时，哪些改动最容易把安全性搞坏？

更细的实现细节，建议同步参考：

- server 端： [认证与安全接入](/collaboration_tools/核心模块详解/open-collaboration-server模块/认证与安全接入/认证与安全接入.md)
- simple login： [简易登录机制](/collaboration_tools/核心模块详解/open-collaboration-server模块/认证与安全接入/简易登录机制.md)

## 我们默认怎么用：开发/内网用 simple login

在日常开发或内网环境里，最常见的选择是 simple login：填一个用户名（可选 email）就能拿 JWT。原因很现实：

- 先把 create/join/sync/fs 代理跑通，比先折腾 OAuth 更能推进项目。
- 对新人来说，simple login 的失败路径也最短，容易定位。

如果你们要对外部署或接企业环境，再考虑 OAuth/Keycloak。

## token 怎么走：pollToken -> loginToken(JWT) -> roomToken(JWT)

这套系统里 token 大致分三类：

- `pollToken/confirmToken`：登录轮询 token（短时有效）。
- `loginToken`：用户级 JWT（登录后拿到，用于调用需要身份的 API）。
- `roomToken`：房间级 JWT（加入房间后拿到，用于实时连接进入 room）。

你在排障时只要分清“现在用的是哪一个 token”，很多现象会立刻合理。

## 通信安全的第一道闸：连接阶段必须带 JWT 和公钥

server 在实时连接接入时，会强制要求 headers 里带 JWT 与 public key：

```ts
const jwt = headers['x-oct-jwt'];
if (!jwt) {
    throw this.logger.createErrorAndLog('No JWT auth token set');
}
const publicKey = headers['x-oct-public-key'];
if (!publicKey) {
    throw this.logger.createErrorAndLog('No encryption key set');
}
let compression = headers['x-oct-compression']?.split(',');
if (compression === undefined || compression.length === 0) {
    compression = ['none'];
}
```

这段代码解决的问题是：“不允许匿名/无加密能力的连接进入协作房间”。因此你看到 “No JWT auth token set / No encryption key set” 时，不要只看客户端 UI，应该回到登录流程与协议连接流程（见 [认证机制](/collaboration_tools/安全与认证/认证机制.md)）。

## 广播消息的一个关键细节：按目标裁剪 encryption key

消息级加密下，broadcast metadata 里会带多把 key。server 广播时会按目标 peer 裁剪：

```ts
const peerKey = message.metadata.encryption.keys.find(e => e.target === peer.id);
if (peerKey && BroadcastMessage.isEncrypted(message)) {
    const messageWithSingleKey: EncryptedBroadcastMessage = {
        ...message,
        metadata: {
            ...message.metadata,
            encryption: { keys: [peerKey] }
        }
    };
    peer.channel.sendMessage(messageWithSingleKey);
}
```

这段代码解决的问题是：“广播要发给所有人，但不应该把所有人的 key 都发给每个人”。二开时如果你新增 broadcast 消息，建议不要改这个策略。

## JWT 私钥：开发环境能跑不代表生产环境安全

JWT 的生成/校验都依赖私钥。`CredentialsManager` 在校验 JWT 时会从配置里取 `oct-jwt-private-key`，如果没有配置，会走一个“开发可用”的回退逻辑（源码：`packages/open-collaboration-server/src/credentials-manager.ts`）：

```ts
async verifyJwt<T extends object>(jwt: string, verify: (obj: unknown) => obj is T): Promise<T> {
    const key = this.getJwtPrivateKey();
    const { payload } = await jose.jwtVerify(jwt, key);
    if (verify(payload)) {
        return payload;
    } else {
        throw this.logger.createErrorAndLog('JWT payload is not valid');
    }
}

protected getJwtPrivateKey(): Uint8Array {
    const key = this.configuration.getValue('oct-jwt-private-key') ?? getLocalFilename(import.meta.url);
    return Buffer.from(key);
}
```

这段代码解决的问题是：“让本地开发能跑起来”，但它同时也在提醒你：生产环境必须配置好私钥与相关安全策略。并且在 `initialize()` 阶段，如果未配置私钥，server 会输出明确的 warn（这也是你线上排障时的一个重要信号）。

## 二次开发最容易踩的坑（务必避免）

- 放宽 `receiveMessage()` 对 request/broadcast 的加密要求：这会让未加密消息混进系统，后果不可控。
- 在 provider 里绕过 `confirmUser()`，让各认证方式各自签 JWT：会导致 JWT 行为不一致、排障困难。
- 把 redirect URL whitelist 去掉：OAuth/Keycloak 回调极易引入开放重定向风险。

## Summary

- 默认开发/内网环境用 simple login；生产/对外再考虑 OAuth/Keycloak。
- token 主线是：pollToken -> loginToken(JWT) -> roomToken(JWT)。
- 连接阶段强制要求 JWT + public key，是通信安全的第一道闸。
- 广播时按目标裁剪 encryption key，是消息级加密能工程化落地的重要细节。
