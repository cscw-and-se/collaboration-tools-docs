# 多人多 Agent 协同编程研究方向

> 本文于 2026 年 11 月重写。早期版本讨论的是 AI 作为协作参与者、语义合并、协作感知等方向，这两年 Coding Agent 迅速普及，问题已经从人与人协作，变成多人和多个 Agent 一起协作。

[什么是实时协同编程](/rcp/what_is_rcp.md) 讲的是多人如何同时编辑同一份代码，[OT算法 vs CRDT算法](/rcp/ot_vs_crdt.md) 讲的是如何保证大家看到的文本一致。现在每个人手里都有自己的 Coding Agent，一个协作会话里同时有多名开发者和多个 Agent。这篇文档梳理这个场景下值得研究的几个方向，读完你可以知道有哪些问题、每个问题大致是什么样子，以及从哪里入手读文献。

## 适合谁读

- 想为毕设或论文选题的同学。
- 想了解本组研究背景的同学。

## 为什么多人多 Agent 是新问题

只有人参与时，协同工具能做到的是让文本一致，并显示彼此的光标和选区，也就是谁在改哪里。Agent 加入以后，出现了几个新情况。

**修改的速度和数量变了。** 一个人让 Agent 去做一个任务，它可以在很短时间里改动很多文件。如果两个人对任务的理解不一致，这种分歧会通过各自的 Agent 迅速变成大量互相矛盾的修改。

**意图看不见了。** 光标只能说明某人在改哪里，说不出他想做什么。Agent 的任务说明、执行计划和进展，通常只存在于发起者自己的会话里，其他人看不到，Agent 也不知道别人在做什么。

**文本一致不等于程序一致。** CRDT 保证每个人看到的文本相同，但两处互不重叠的修改，仍然可能因为代码之间的依赖关系相互干扰。例如一个人改了函数的返回字段，另一个人的 Agent 还在读旧字段。

**权限和责任变得模糊。** Agent 能执行命令、运行测试、安装依赖、操作 Git。在共享环境里，一次工具调用是谁发起的、会影响谁，都需要重新考虑。

2026 年有一项用户研究也观察到类似现象。它让多名作者在共享文档里使用自己创建的 AI Agent，发现团队会把 Agent 纳入已有的作者身份、控制权和协调规则之中，而不是把它当成团队成员。这篇论文的对象是文档写作而不是编程，但它说明了同样的问题，见 [Collaborative Document Editing with Multiple Users and AI Agents](https://arxiv.org/abs/2509.11826)（CHI 2026）。

## 方向一：让协作者看见彼此的意图

**问题。** 现有工具显示的是位置，而协作需要的是意图。Alice 的 Agent 正在重构接口，Bob 的 Agent 正在基于旧接口写新功能，两个人可能到合并时才发现。

**思路。** 引入一块共享的区域，集中记录开发者的任务意图、团队的约定和 Agent 的工作状态，让所有人和所有 Agent 都能看到，并据此在冲突形成之前就发现任务分歧或工作重叠。这个思路可以追溯到经典的黑板架构，多个知识源在一块共享黑板上协作解决问题。

**怎么读。** 工作空间感知（workspace awareness）的经典框架，以及早期检测并行修改冲突的工作，是理解这个方向的起点。

- Gutwin 和 Greenberg，A Descriptive Framework of Workspace Awareness for Real-Time Groupware，2002。
- Sarma 等，Palantír: Early Detection of Development Conflicts Arising from Parallel Code Changes，2012。
- Erman 等，The Hearsay-II Speech-Understanding System，1980，黑板架构的原始论文。

**难点。** 记录意图要让开发者觉得不麻烦，否则没人愿意写。提示不能太频繁，否则变成打扰。Horvitz 的混合主动界面原则（1999）讨论了这类取舍。

## 方向二：让任务要求变得可检查

**问题。** 开发者通常用自然语言给 Agent 布置任务，但允许改哪些文件、接口不能怎么动、需要通过哪些测试，往往没有说清楚。Agent 可能越界修改、遗漏功能或违反约束，而开发者只能人工对照原始要求检查。

**思路。** 把任务要求整理成结构化的承诺，包括目标、允许的修改范围、接口约束、测试要求和验收条件。执行过程中记录 Agent 做了什么，把这些证据和承诺对照起来，指出哪些满足了、哪些没满足、哪些证据不足。

**难点。** 并行修改和承诺中途调整都会影响检查结果。有些要求难以自动检查，需要判断哪些交给开发者确认。

## 方向三：控制 Agent 能做什么

**问题。** 与单人使用 Agent 不同，共享环境里一次工具调用的发起者和后果的承担者往往不是同一个人。Alice 触发的一条命令，可能删除 Bob 正在使用的文件。现有工具的权限要么以会话为单位授予，粒度很粗，要么只按工具类别设置，不区分是谁触发的、会影响谁。只靠提示词约束 Agent 又不稳定。

**思路。** 根据一次操作本身及其对共享项目和其他协作者的影响来判断风险，再分级处理。风险低的直接执行，风险中等的提示，风险高的需要人批准。对于实验性的修改，让 Agent 在独立的工作区或分支里做，确认后再合并回会话。

**难点。** 管得太严会削弱 Agent 完成任务的能力，管得太松又有风险，需要在两者之间找到平衡，并且尽量少打扰人。

## 方向四：在冲突发生之前就预防

**问题。** 版本管理工具通常在合并时才发现冲突。实时协同里，文本层面的冲突由算法自动解决，但语义层面的冲突仍然存在。此外，Agent 可能依据已经过时的代码继续工作，因为别人的修改它看不到。

**思路。** 已有研究提出了基于依赖关系的自动锁定，在你修改某处代码时，把依赖它的代码也一并保护起来。在多人多 Agent 场景下，可以进一步研究预约机制，让开发者和 Agent 在动手前协调修改范围、编辑权限和占用状态，并处理任务等待、取消和异常退出带来的占用失效问题。

**怎么读。** 早期版本的研究方向里提到的语义合并也属于这个问题。比如你把 `getData()` 重命名为 `fetchUserData()`，队友在 `getData()` 里加了参数，理想的合并工具能够理解这两处修改的意图，自动得到 `fetchUserData(newParameter)`。

- Brun 等，Proactive Detection of Collaboration Conflicts，2011。

**难点。** 锁得太多会拖慢协作，锁得太少又拦不住冲突。需要通过实验来衡量预防效果和协作开销。

## 方向五：追踪一个任务从头到尾的上下文

**问题。** 一个任务往往经历需求澄清、方案讨论、多次尝试和测试验证。现有的 Agent 工具里，对话、代码差异、工具调用记录和测试结果分散在不同界面，缺少围绕具体任务的组织。当任务经历多轮修改，或者你在多个任务之间切换时，很难解释某处修改的原因，也难以判断哪些测试支持当前结果。

**思路。** 围绕开发任务把对话、代码变更、工具执行和测试结果关联起来，建立可以查询和追踪的关系，支持任务中断后快速恢复上下文，并探索让大语言模型生成有依据的任务摘要。

**难点。** 摘要要有依据，不能只是流畅的复述，否则会误导开发者。

## 仍然开放的问题

早期版本里有两个方向目前还没有太多进展，这里保留。

**编程教育场景。** 编程教学目前主要靠屏幕共享，或者老师走到学生旁边帮忙排查。实时协同可以让老师同时看到所有学生的进度，发现有人卡住时进入他的视图单独指导。如今学生身边还有 Agent，教师还需要了解学生和 Agent 之间发生了什么。

**单人开发与多人协作的衔接。** 单人开发和团队协作目前是割裂的，先在本地开发，再通过 `git push` 和 Pull Request 异步同步。如果能降低切换成本，遇到问题时直接开启一个协同会话，把链接发给别人一起调试，改动仍留在自己的分支里，求助会简单很多。

## 怎么在这个方向上做研究

本组有一套实时协同智能编程底座，可以直接在上面实现想法并做用户实验。上手的方法见 [项目概览](/collaboration_tools/project_overview.md) 和 [如何运行](/collaboration_tools/how_it_works.md)，整个毕设的推进顺序见 [毕设与论文时间线](/research/thesis_timeline.md)。

选择方向时，可以先问自己三个问题。第一，我能不能用一个具体的协作场景把这个问题讲清楚。第二，我能不能在底座上做出一个原型。第三，我能不能设计一个实验来判断它有没有用。三个问题都能回答，就是一个合适的起点。
